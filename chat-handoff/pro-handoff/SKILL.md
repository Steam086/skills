# Pro Handoff

Use this workflow when the user explicitly invokes `$pro-handoff` in Codex or `/skill:pro-handoff` in Pi. Pi expands the command and appends its arguments to these instructions. Resolve `scripts/cli.py` relative to this skill directory and run it with the project's instructed Python 3.11+ interpreter. The engine runs offline. The user moves the ZIP, Prompt and response between their local agent and ChatGPT Pro.

## Choose the operation

- Bare invocation or a task description → `export --type full`. Use the user's task, the active conversation, and the selected session's current objective. If none supplies a task, provide an architecture orientation with specific open questions grounded in the project.
- `sync` → `export --type delta`. Start with the confirmed base plan and manifest from `status`. Retain still-relevant baseline files while adding new work and evidence. The engine falls back to a standalone full export when no base is confirmed. Tell the user which type was produced.
- `recover` → `recover`. Reinspect code and tests underlying the accepted decisions and verified facts, including any stale evidence flagged by `status`. Reconstruct the current architecture and implementation directly from evidence. Include prior approaches, supersession reasons, and validation results so a fresh Pro conversation can continue independently.
- `status` → `status`. Show the active session, objective, current state, generated export, confirmed delivery, and last import. Summarize only shareable excerpts from any imported advisory text.
- `sent [EXPORT_ID]` → `mark-sent EXPORT_ID`. With no ID use the selected session's latest generated export and report which one was recorded. The invocation means the user has delivered that ZIP.
- `import <path>` or `import` with pasted content → `import-response <path>` or `import-response -`. Use the actual JSON or Markdown with a fenced JSON block. Copy pasted content verbatim into stdin or a private temporary file. If neither was supplied, request it. See [Import and local review](references/workflow.md#import-and-local-review).
- `init <name>` → `init --session <name>`. `use <name-or-id>` → `use <name-or-id>`. `review` records locally reviewed state using the workflow reference.

Pass `--project` for a user-specified directory and `--session` for a user-selected session. Omit `--session` to use the active session. In a non-Git project, use the intended project directory as the root. A named export can create a new session.

## Plan and publish

1. Read [Planning and selection](references/workflow.md#planning-and-selection). Run `scan --json` and `status --json` first. For large inventories, save the scan privately and inspect the discovery fields and paths relevant to the task. Read task-relevant files and use scoped searches to trace dependencies. Use actual worktree contents, Git status, relevant prior decisions, and the conversation you can access.
2. Write a structured Handoff Plan JSON in a private temporary location. Include the evidence-backed project overview, file reasons, current progress and verification, questions, and desired Pro output. Declare `required_context`: map each question that depends on local evidence to its necessary project-relative files and explain why they are needed. Independently retrace the task's call paths, interfaces, configuration and tests to check this list; do not just reread the selected paths. Rebuild older plans that lack this field. Resolve relevant local skills yourself while planning. Write any rules or checks that materially affect Pro's answer directly into the current `prompt` as task guidance; don't send a raw skill catalog or ask Pro to choose skills. Attach originals only when needed as [reference evidence](references/workflow.md#skill-guidance-and-reference-attachments). Use the plan's optional `state_review` for locally verified facts and decisions already accepted by the user. Write the dedicated task brief in the user's language for this run. Identify missing history or evidence explicitly. The engine takes this plan as an input.
3. Run `preview --type <full|delta|recovery> --plan <path>`. Read `publishable`, `blocking_gaps`, `zip_bytes`, selected paths, attachments, exclusions and coverage gaps. If `publishable` is false, do not publish. First try to safely complete local discovery and selection, then preview again. If necessary evidence remains unavailable or needs a user decision, pause the handoff and ask the user as described below. Never substitute a partial ZIP for this pause. When `preview_required` is true, show the task, scope, representative source paths, any `new_source_paths`, counts, compressed size, exclusions, the task guidance being shared, and every selected reference attachment path with its selection reason. Obtain the user's confirmation and use `--approve <preview_token>`. Keep the same plan, session, and budget. An explicit `--yes` in the user's request authorizes noninteractive export. Continue previewing for coverage, and pass `--yes` only when the user supplies it. If a preview is stale, rerun it and present the change.
4. Run the chosen publish command with the same plan and options. For sync, state the exact base and work completed since it. Report the ZIP and external Prompt paths, export ID, file counts, compressed bytes, coverage gaps and exclusion reasons. Include the generated Prompt verbatim in a copyable Markdown block using a fence longer than any backtick run in the Prompt. Link the two files, then tell the user to upload the ZIP and paste the Prompt. A generated export remains unconfirmed until `sent` or a matching Pro reply.

## Blocked handoffs

Critical selections, `required_context` files, and citations backing current verified facts or accepted decisions must be available in the target snapshot. Full and recovery exports carry those files; deltas may reuse unchanged files from their exact confirmed base. Superseded decisions and unreviewed Pro advice are not automatically current requirements. Check stale evidence rather than treating its old digest as current proof.

For ZIP budget blockers, first reduce nonessential material or ask the user to approve a larger budget. Keep all necessary evidence. When local investigation cannot safely resolve a blocker, stop the export loop and explain what is missing, why it is necessary, which question or conclusion it affects, and the smallest evidence or scope decision needed from the user. Do not retry the same blocked command, fabricate replacement files, demote required files, delete citations, or weaken the declared requirements merely to pass the gate. A genuine scope change requires the user's decision and a revised plan and preview. Security filtering stays enabled; request safe redacted evidence rather than credentials. `--yes` and preview approval authorize sharing, not an incomplete handoff. Nonessential omissions may remain documented warnings. Do not report completion, offer a previous ZIP as this attempt's result, or mark delivery for a blocked attempt.
