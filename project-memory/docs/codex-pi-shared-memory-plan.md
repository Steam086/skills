# Codex 和 Pi 共用项目记忆的适配计划

## 目标

让 Codex CLI 和 Pi 在同一个项目中使用同一份源码记忆、配置和检索索引。两边通过各自的宿主适配器调用共享核心，不复制两套记忆，也不把仓库知识混入 Codex 的用户级原生记忆。现有 Pi 记忆必须可迁移并可回滚。

记忆根目录采用宿主无关的项目路径：`<project>/.project-memory/`。Codex 与 Pi 使用相同的项目根解析规则；可显式传入根目录，未传入时从当前目录解析项目根。该目录默认加入项目忽略规则，记忆仍留在本机。

## 目标结构

```text
.project-memory/
  config.json
  topics/
  daily/
  recovery/
  diagnostics/
  .qmd/
    index.yml
    index.sqlite
```

主题、旧格式笔记、恢复记录和 QMD 索引都以此目录为唯一项目数据源。QMD 配置放在 `.project-memory/.qmd/`，因为 QMD 2.8.3 的项目级信任逻辑要求配置目录名为 `.qmd`；QMD 命令从 `.project-memory/` 运行，因此该索引仍以共享根为作用域。模型权重可继续使用机器级共享缓存，因为它们是检索依赖，不是记忆内容。两种宿主不得各自初始化独立的数据库或 QMD 索引。

## 目标架构

```text
                    同一份 SKILL.md
               检索时机、核验与写入规则
                    /           \
             Pi 扩展适配器     Codex MCP 适配器
                    \           /
                    共享记忆核心
       存储、配置、权限、检索、来源新鲜度
                            |
              <project>/.project-memory/
```

共享核心提供与宿主无关的服务接口，并拥有所有读写规则。两个适配器只负责宿主工具的注册、参数转换和结果呈现。统一工具契约沿用当前的 `memory_search`、`memory_read`、`memory_upsert`、`memory_write`、`scratchpad`、`memory_forget`、`memory_restore` 和 `memory_status`；两边对相同参数执行相同校验并返回相同结果结构。

同一份 `SKILL.md` 是检索和写入策略的唯一来源。Pi 包直接加载它；Codex 的 skill 安装入口从该文件部署或引用，并通过检查防止内容分叉。Skill 只提供模型操作规范，实际读写必须通过共享核心工具完成。

## 改造范围

| 区域 | 计划改动 |
| --- | --- |
| 共享核心 | 将 `extensions/project-memory.ts` 中的工具处理和业务编排拆到 `lib/` 服务层；存储、修订冲突、来源哈希、分页、检索和访问控制不得依赖 Pi 类型或 UI。 |
| Pi 适配器 | 保留 Pi 扩展入口和 `/memory-mode`、`/memory-access` 命令；将命令解析后得到的权限上下文传入共享服务。移除适配器中重复的存储和检索逻辑。 |
| Codex 适配器 | 增加本地 stdio MCP 服务，调用同一共享服务并暴露统一工具契约。Codex 启动时绑定当前项目根；服务不得回退到用户级或其他项目的记忆目录。 |
| Skill 和安装 | 将通用策略保留为单一 `SKILL.md`；Pi manifest 和 Codex skill 安装配置都引用该规范。安装程序为当前项目建立 `.project-memory/` 并更新忽略规则，不自动授权宿主信任。 |
| QMD | 将配置和索引位置改为 `.project-memory/.qmd/`；两种宿主只查询同一个索引。读取操作不得隐式下载模型、启动服务、迁移索引或授予信任。 |
| 兼容性 | 保留既有 Pi 工具名称和行为。旧记忆迁移必须显式执行，遇到目标冲突时停止，不静默覆盖或合并。 |

首先解耦 `memory-env.cjs` 的 Pi 专用路径和全局 `process.env` 修改；为共享服务传入显式 `projectRoot`、`memoryRoot`、权限和取消信号。检查 `memory-store` 的并发写行为，保证两个宿主进程同时修改同一主题时仍使用修订检查和跨进程锁，避免丢失更新。

## 实施阶段

### 阶段一：定义数据目录与服务契约

1. 新增统一的项目根和记忆根解析器，支持显式 `--root`，并拒绝符号链接和包目录误用。
2. 定义共享服务 API、工具 JSON Schema、错误码、分页边界和权限上下文。
3. 将访问控制、手动写入规则、`code-research` 写入条件、源码锚点和修订校验集中到共享层。
4. 确认 Codex MCP 服务进程可以使用当前 Node/QMD 依赖及项目配置。

**完成条件：** 服务层可以在没有 Pi SDK 的独立进程中初始化；所有路径由调用方显式提供；对外工具契约有一份规范。

### 阶段二：抽取共享核心并保留 Pi 行为

1. 将搜索、读取、更新、遗忘、恢复、旧格式笔记操作和状态查询从 Pi 扩展移动到共享服务。
2. 将配置、诊断、QMD runtime 接口从隐式环境变量改为显式依赖。
3. 把 Pi 扩展缩减为工具注册、命令入口和共享服务调用。
4. 新适配器遇到旧记忆时要求先显式迁移；旧目录和文件保留为回滚来源，但不会被新版本继续读写。

**完成条件：** Pi 的工具名、访问门控、搜索结果、记忆格式和来源新鲜度保持兼容，且 Pi 适配器没有复制业务规则。

### 阶段三：增加 Codex MCP 适配器

1. 新增 `scripts/memory-mcp.mjs`，通过 stdio 暴露共享工具。
2. 从 Codex skill 安装配置注册该 MCP 服务，并将当前仓库根传给服务。
3. Codex 工具使用与 Pi 相同的工具名、参数限制、错误码和字符预算。
4. 提供用户可操作的读写控制入口；权限变化必须来自宿主命令或服务启动配置，不能由模型调用记忆工具自行授权。

**完成条件：** Codex 能从当前项目的统一目录搜索并读取已有主题；在 Codex 中新增或修订的主题能立即被 Pi 读取，反向亦然。

### 阶段四：单目录迁移与安装

1. 新增 dry-run 迁移命令，识别 `.pi/memory/`、`.pi/memory-config.json` 和现有 `.qmd` 配置。
2. `--apply` 复制到 `.project-memory/`，记录文件清单和哈希；不删除来源、不覆盖已有目标。
3. 迁移后由用户显式重建或验证 QMD 索引；不自动下载模型、启动服务或授予信任。
4. 提供回滚说明；切换完成前只允许从一个指定目录写入，禁止双写。

**完成条件：** 迁移前后主题 ID、修订、锚点、旧格式内容和恢复记录一致；校验失败时旧目录仍完整可用。

### 阶段五：双宿主验收

- 同一项目中从 Pi 写入、Codex 搜索和读取，再从 Codex 更新、Pi 读取。
- 两边对相同主题报告相同修订号、来源哈希和 stale 状态。
- 读关闭、写关闭、off、手动模式和 `code-research` 模式在两个入口有一致结果。
- 并发更新、修订冲突、损坏文件、迁移冲突和取消中的搜索不会造成静默丢失或权限绕过。
- 两边不会生成第二个记忆根、第二个 QMD 索引或未经授权的模型/服务初始化。
- 运行 Pi 原有回归测试，并新增共享核心和 Codex MCP 的契约测试。

## 兼容与边界

Codex 的原生本机记忆继续独立运行，用于跨项目的个人偏好和工作背景；本系统只保存项目源码知识。两者不自动同步，也不相互复制内容。共享目录默认只在本机项目中使用；团队跨机器共享、版本控制记忆正文或云端同步属于后续独立决策。

迁移回滚：停止新版本宿主并恢复旧 package/settings，迁移不会修改旧目录。切换后的新写入只进入 `.project-memory/`；如需在有新写入后回退，先把这些新记录人工复制回旧格式位置，再启动旧版本，避免丢失切换后的内容或并行双写。迁移稳定后，再考虑将 `.pi` 命名从安装脚本、环境变量和文档中彻底移除。模型缓存可以继续放在机器级共享缓存中，避免在每个项目内复制大文件。

## 工作量估计

这是中等规模的适配，不需要重写记忆存储或检索算法。核心工作是从 Pi 扩展抽出服务边界、增加 MCP 入口、统一数据根目录和安全门控，再为双进程使用补足并发与兼容性检查。保持现有记忆格式并分阶段迁移，可把目录切换风险隔离在第四阶段。
